# 2026-07-17 ARM64 PPU hardware-FTZ upstream slice

## Result

Adapt official RPCS3 commit [`e9f833a2`](https://github.com/RPCS3/rpcs3/commit/e9f833a2e8ad0d02652c18f69232ccdde5c5999f), `PPU LLVM: Accelerate NJ handling in FTZ environment`, to the Android fork. The work is source- and host-validated and promoted only for Eternal Sonata (`BLUS30161`). It is not installed or measured on the AYN Thor, so this is not a silicon temperature or device-speed claim.

The matched Windows first-battle A/B kept performance effectively unchanged at roughly 120 FPS while reducing sampled RPCS3 process CPU from `47.83%` to `37.60%`, a `21.4%` reduction. Sampled total host CPU fell `22.6%`. That is strong work/power-direction evidence and justifies the title-scoped profile promotion, but Thor temperature remains unproven.

## Research direction

The useful current research signal is work elimination and phase-aware control, not blanket clocks or affinity:

- [Phase Matters: Phase-Aware Dynamic Compilation for Emulation](https://arxiv.org/abs/2606.27906) supports targeting distinct startup, compile, and steady-gameplay phases rather than applying one aggressive policy everywhere.
- [Learning Rewrite Rules for Dynamic Binary Translation](https://arxiv.org/abs/2402.09688) supports eliminating redundant translated work, which is the mechanism used here.
- [Partial Cross-Compilation for Dynamic Binary Translation](https://arxiv.org/abs/2512.00487) reinforces moving recurring translation work out of hot execution paths.
- Android's [Performance Hint API](https://source.android.com/docs/core/perf/performance-hint-api) and [ADPF thermal guidance](https://developer.android.com/games/optimize/adpf/thermal) are useful longer-term control surfaces, but generic performance hints can request more performance and therefore more heat. The Thor's Android 13 base also cannot use the newer API-35 power-efficiency session mode. No ADPF behavior was enabled in this slice.

## Upstream mechanism and fork adaptation

With `Set DAZ and FTZ` enabled, the host floating-point environment flushes most PPU vector denormal results in hardware. The previous fork still generated manual `VecHandleDenormal` masks after nearly every vector floating-point result, duplicating that work.

The adaptation:

- skips generic manual PPU LLVM NJ/denormal fixup when hardware FTZ is active;
- preserves explicit manual flushing for `VEXPTEFP`, `VLOGEFP`, `VMAXFP`, and `VMINFP`, matching official upstream's sensitive-operation exceptions;
- applies the same guarded selection to the PPU interpreter path;
- adds `uses_hardware_ftz` to PPU object-cache identity so FTZ-on and FTZ-off code never reuse incompatible compiled objects;
- preserves the Android fork's legacy `PPU LLVM Java Mode Handling` behavior when FTZ is off;
- keeps the global default off;
- enables `Set DAZ and FTZ: true` only in the managed BLUS30161 profile and the four Eternal Sonata templates generated by `tools/push_eternal_sonata_thor_profile.ps1`.

The Windows lab harness gained `-PpuDazAndFtz Keep|On|Off`. It writes only the per-run copied config and logs the exact selection, so the A/B did not mutate the normal RPCS3 configuration.

## Eternal Sonata A/B

Common conditions:

- title: legally owned Eternal Sonata, `BLUS30161`;
- route: exact title, save load, Path to Tenuto field, first-battle tutorial prompt, active battle, live battle, and hold;
- all CPU cores available;
- vblank `240`, gameplay near `120 FPS`;
- external host contention classified clean;
- exact run-local config captured in each directory.

| Condition | Run | Correct route | Battle FPS | RPCS3 CPU | Total CPU | GPU engine sum |
|---|---|---:|---:|---:|---:|---:|
| FTZ off | `20260717-213101-upstream1d657c4-ftz-off-allcore-uncap240-first-battle-windows` | yes | `119.998`* | `47.83%` | `54.80%` | `33.93%` |
| FTZ on, cold cache | `20260717-213358-upstream1d657c4-ftz-on-allcore-uncap240-first-battle-windows` | no comparable route | n/a | n/a | n/a | n/a |
| FTZ on, warm cache | `20260717-213648-upstream1d657c4-ftz-on-warm-allcore-uncap240-first-battle-windows` | yes | `119.964` | `37.60%` | `42.40%` | `32.63%` |

`*` The FTZ-off FPS mean excludes one `113.95 FPS` screenshot-capture outlier at 145 seconds. Including it gives `119.494 FPS`; the other eleven periodic samples average `119.998 FPS`. FTZ-on's twelve periodic samples average `119.964 FPS`, ranging `119.90` to `120.07`.

The three steady-battle one-second host samples were:

| Condition | Seconds | RPCS3 CPU samples | Total CPU samples | GPU samples |
|---|---|---|---|---|
| FTZ off | `93, 120, 150` | `49.9, 52.1, 41.5` | `58.5, 61.1, 44.8` | `25.2, 26.9, 49.7` |
| FTZ on | `92, 120, 150` | `36.4, 39.4, 37.0` | `41.9, 46.0, 39.3` | `32.1, 34.4, 31.4` |

Derived deltas:

- FPS: `119.998 -> 119.964`, effectively unchanged (`-0.028%`);
- RPCS3 CPU: `47.83% -> 37.60%`, down `10.23` percentage points or `21.4%` relative;
- total CPU: `54.80% -> 42.40%`, down `12.40` percentage points or `22.6%` relative;
- GPU engine sum stayed similar enough to support a CPU-work explanation rather than a workload collapse.

Every matched RPCS3 CPU sample was lower with FTZ enabled. Both comparable runs reached and held the correct battle route. Symmetric scans of both RPCS3 logs found no actual access violation, Vulkan device loss, segmentation fault, assertion failure, or unhandled exception.

The cold FTZ-on run was stopped by the harness's probable-crash/small-black title classifier around 79 seconds. Its log instead showed the new FTZ cache identity compiling dozens of PPU modules and normal game initialization beginning near the cutoff, with no fatal marker. It is classified as cold-cache/tooling evidence, not as a correctness failure and not included in the A/B.

## Thermal and deployment boundary

No ADB query, install, launch, or temperature read was made during this slice. The Thor remains on APK `24F3F267...F87F`. The prior host-only `8DAF...A1DF` candidate also remains uninstalled.

Do not turn the Windows CPU reduction into a Thor temperature claim. The next device sequence remains:

1. wait for a separately cool round;
2. pass the strict three-sample `<35 C`, net-rise `<=1 C`, PID-absent install-only gate;
3. install without launch and stop for that round;
4. in another independently cool round, spend at most one guarded bounded route with two-second thermal polling, confirm at `60 C`, stop at `68 C`, and hard-limit at `72 C`;
5. compare correctness, FPS, time-to-thermal-stop, and temperature trajectory against the exact installed control.
